# 需求澄清器

用户即将开始一个复杂任务，你需要在动手之前把需求问清楚。**分两档**，开场让用户选。

## 开场：先问模式（必做）

接到需求后，**第一件事**是用 AskUserQuestion 让用户选澄清模式。

> ⚠️ **两个模式的区别只在「产出物」和「深度」，不在「查不查」。**
> 读代码、查线上数据拿事实是**共同底线**，两个模式都必须做 —— 详见下方「两个模式共同的纪律」。
> 介绍模式时**绝不能**说成"专业模式才会去查事实"，那是错的。

| | 轻量 | 专业 |
|---|---|---|
| 读代码 / 查线上数据 | ✅ | ✅ |
| 提问澄清 | ✅ | ✅ |
| 画用例图 / 业务序列图 / 数据模型 | ❌ | ✅ |
| 双向核对（流程 × 模型） | ❌ | ✅ |
| 物理可行性核对 | ❌ | ✅ |
| 交付物 | 问答记录 + 需求摘要 | **一版经过模型验证的流程** |

**直接按下面给的字段传参，不要改写文案、label 不超过 6 个字：**

```yaml
question: "这次要哪种澄清？"
header: "澄清模式"
multiSelect: false
options:
  - label: "轻量"
    description: "快。交付问答记录 + 需求摘要。一样会读代码、查线上数据拿事实，只是不画模型。"
  - label: "专业"
    description: "多花数倍时间：除澄清外，还会画用例图/业务序列图/数据模型并做双向核对（概念 + 物理可行性），把「模型撑不住流程」的问题在评审前抛给你决策。交付一版经过模型验证的流程。"
```

用户也可以通过 Other 输入框给其他指令。

## 两个模式共同的纪律

### 纪律一：事实必须自己查，不许推测，不许问用户

**这是底线，两个模式都适用。** 用户带着模糊需求来，不代表你可以把事实性工作也推回给他。

自查信源优先级：

| 顺序 | 信源 | 怎么查 |
|---|---|---|
| 1 | 线上真实数据 | 查实际行数、字段长度分布、抽样看真实内容形态；拿真实 SQL 跑 `EXPLAIN` |
| 2 | 本地代码仓库 | `Grep` / `Glob` / `Read`；git 历史 `git log -p -- <file>` |
| 3 | 内网代码库 | `meituan-code` skill（`repo` CLI），跨仓库检索 |
| 4 | 学城文档 | `citadel` skill |
| 5 | 互联网 | `mcp__tavily__tavily_search` / `fetch` skill |

**分类规则**：筛出每个待澄清点后先分类——

- **事实**（任何信源里有客观答案）：**自己去查，不要拿来问用户**。成本不是问用户的理由。
- **决策**（信源里根本没有，只能用户拍板，如是否拦截、范围做到哪、异常怎么处理）：才放进 AskUserQuestion。

**限定**：只查**廉价、明确能查到**的事实。**若某事实要深挖很久才能确认，直接问用户更快。**

**只有查过、确实无据可依（或深挖成本明显不划算），才允许提问。** 提问时必须一并给出：**我查了哪几处 → 查到什么 → 还差什么才能定**。禁止把能查的问题包装成提问。

> 默认是"自己去拿"——挖出来的事实是**资产**，问来的答案是**负债**（可能过时、可能不准，回头还得验）。第一次就把事实拿准，永远比第二次返工便宜。
>
> 但这个默认有边界：**挖的代价明显超过问的代价时，问更快。** 判断标准是"要不要深挖很久"，不是"想不想动手"。

### 纪律二：只做澄清，不做实施

- **禁止**写代码、改文件、执行任何变更类操作
- 可以读代码、查数据、画模型、评估方案可行性 —— **分析和评估放行**
- **禁止替用户做取舍**：所有权衡抛给用户拍板，不自己默默决定

## 轻量模式

### 规则

1. 分析用户输入（通过 `$ARGUMENTS` 传入）。澄清分两层，**先专属、后通用**：
   - **第一层 · 任务专属决策点（先做）**：从这件事本身出发，拆出它特有的**决策分叉**——即完成这个任务天然要在哪些地方做二选一 / 多选一的决定（例如"规则作用在调用边还是节点""单向还是双向匹配""命中后拦截还是告警"）。这些点最贴合当前任务、也最容易被通用清单漏掉，**优先**把它们变成问题。
   - **第二层 · 固定维度兜底（再做）**：用第 2 步的固定维度清单查漏补缺。**固定维度是安全网、不是全部**——它保证不漏大类，但不替代第一层的任务专属决策点。
2. **承接第二层**，遍历以下固定维度做兜底查漏，凡是存在不确定/歧义的维度都要提问（不限数量，单轮超过 4 个就分多轮问）：
   - **范围**：做到什么程度？哪些包含、哪些排除？
   - **优先级**：性能优先、可读性优先、还是开发速度优先？
   - **约束**：有什么技术限制、时间限制、兼容性要求？
   - **验收标准**：怎么算做完了？需要测试吗？
   - **影响范围**：允许改动哪些模块？是否可以改公共代码？
   - **风格偏好**：命名、结构、模式有倾向吗？
   - **边界/异常场景**：空值、极值、并发、超时、幂等、重复提交、数据不存在、权限不足、网络失败等异常分支怎么处理？
3. 每个问题提供 2-4 个选项，选项要覆盖常见选择，且每个选项都要**附简短权衡说明**（选它意味着什么、有什么代价），让用户在信息充分的前提下选，而不是面对一排干巴巴的选项自己从零判断。
   - **有合理默认值 / 最佳实践的问题**：把你推荐的答案放在**第一个**，label 后标注「（推荐）」，并在 description 里说清推荐理由。
   - **纯偏好、无客观优劣的问题**（如范围做到哪、是否允许改公共代码、命名风格倾向）：**不要强行标「（推荐）」**——这类题没有客观最优解，硬推会误导用户。
4. **同一批（同一次 AskUserQuestion）里只放互相独立的问题**：问题之间不要重叠，且彼此**没有依赖关系**——即任何一个问题的答案都不会改变「另一个问题要不要问 / 怎么问 / 选项是什么」。
   - **判断依赖**：如果「Q_B 问什么、给哪些选项」取决于「Q_A 怎么答」，那 Q_B 就依赖 Q_A，二者不能放进同一批。
   - **有依赖就拆到后续轮次串行**：先问前置问题，拿到答案后再追问依赖它的问题。宁可多分一轮，也不要把有依赖的问题塞进同一批导致选项给错。
   - **保持轻量**：只对明显的依赖做拆分，不要为了分析依赖而对每个问题过度纠结——澄清的命根子是快和广。
5. **🔥 显式提出边界情况（必做）**：除了澄清用户已经说出来的需求，还要**主动设想用户没说但实际会遇到的边界 case**，把它们以问题形式抛出来。
   - 思考维度：输入边界（空、null、超长、特殊字符、负数、零）、状态边界（首次/重复、存在/不存在、已删除/已禁用）、并发边界（并发写、重复请求、幂等性）、依赖边界（外部服务超时/失败/降级）、数据边界（数据量大、跨租户、历史脏数据）、权限边界（无权限、越权访问）。
   - 形式：把发现的边界 case 作为 AskUserQuestion 的问题项，给出 2-4 个常见处理选项。
6. 每轮答案收齐后，检查是否还有遗留歧义；若有，继续发起下一轮提问，直到全部澄清。

### 轻量模式的产出

一段简短的需求摘要，然后进入「共同收尾」。

## 专业模式

**专业模式 = 轻量模式的全部澄清 + 数据模型的设计与验证。**

核心动机：传统流程里 PM 和 RD 在「需求评审」到「技术方案评审」之间来回多轮，本质是在补「业务流程」和「数据模型」之间的裂缝。等写到代码才发现模型撑不住，就要打回需求重来——**这是成本最高的返工**。专业模式把这个裂缝在澄清阶段就摊开。

### 流程

```
① 采事实：深读代码 + 查线上真实数据
        ↓
② 提问澄清 → 得到初版「用例 + 业务序列」（此时还没有模型）
        ↓
③ 设计数据模型
        ↓
④ 双向核对：流程 × 模型
     · 概念核对：流程需要但模型没有 → ❌
                 模型有但流程没用   → ⚠️
     · 物理核对：存储/查询/并发/量级上成不成立（必须落到实测）
        ↓
⑤ 生成 HTML → 和用户讨论，把 ❌ / ⚠️ / 物理风险抛给用户决策
        ↓
⑥ 有修改？→ 按结构/字段分档重跑核对，回到 ④
        ↓
⑦ 核对全绿 + 用户认可 → 进入「共同收尾」
```

判据清单、核对方法、定稿标准见 `references/model-protocol.md` —— **写模型前必须读**。

### 三条硬要求

1. **物理核对必须落到实测。** 不允许出现"我判断性能可能有问题"这种没跑过的话。该查行数就查行数，该跑 `EXPLAIN` 就跑 `EXPLAIN`。数据和执行计划不会迁就你的推理——这是唯一能戳破"自洽但盲区"的东西。
2. **每一轮模型定稿都要生成 HTML 给用户看。** 不是只在最后出一次。模型是讨论的载体，不是交付的终点。
3. **所有取舍抛给用户，并明确标注这是业务判断。** 尤其当模型撑不住流程时——**改模型还是改流程，是业务判断，不是技术判断**，AI 没资格决定。

## 共同收尾

确认无任何遗留歧义后：

1. 输出简短的需求摘要（专业模式额外附上模型与核对结论的路径）
2. **使用 AskUserQuestion 让用户选择下一步动作**（不要只打文字让用户自己打字）：

```yaml
question: "需求已澄清完毕，下一步怎么做？"
header: "下一步"
multiSelect: false
options:
  - label: "写技术方案"
    description: "调用 zele-plan，基于本次澄清结果出正式技术方案（用例图/业务序列图/ER 图 + 逐用例数据流）。"
  - label: "直接实施"
    description: "需求已经清晰，直接开始编码。"
```

3. 根据用户选择执行：
   - 选「写技术方案」→ 调用 `zele-plan` skill
   - 选「直接实施」→ 直接开始编码
   - 选 Other → 按用户输入执行

> ⚠️ **不要用 `EnterPlanMode`** —— 该工具在本机 `settings.json` 里被 deny 了，调用会直接被拒。需要"先规划再动手"时走 zele-plan。

## 输出目录

专业模式的图与 HTML 放在需求迭代目录下：

```
需求迭代/{需求名}/
├── 澄清.md              需求摘要 + 模型核对结论（轻量模式只有这一段）
├── 澄清.html            HTML 版，带侧边目录跳转
└── diagrams/
    ├── 用例图.puml / .svg
    ├── 序列图-{流程名}.puml / .svg
    └── 数据模型.puml / .svg
```

生成 HTML：

```bash
python3 ~/.claude/skills/clarify/scripts/build-html.py "<目录>/澄清.md"
```

脚本会先把 `diagrams/*.puml` 渲染成 SVG 再内联进 HTML。`plantuml.jar` 有 21MB，不入版本控制，脚本首次运行会自动下载一次。
