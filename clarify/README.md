# clarify

需求澄清器。用户带着模糊需求来，通过多轮 AskUserQuestion 把需求问清楚。分两档。

## 两档模式

| | 轻量 | 专业 |
|---|---|---|
| 查代码 / 查线上数据 | ✅ | ✅ |
| 提问澄清 | ✅ | ✅ |
| 画用例图 / 业务序列图 / 数据模型 | ❌ | ✅ |
| 双向核对（流程 × 模型） | ❌ | ✅ |
| 物理可行性核对 | ❌ | ✅ |
| 交付物 | 问答记录 + 需求摘要 | **一版经过模型验证的流程** |

开场用 AskUserQuestion 让用户选，选项里会把代价讲清楚。

## 为什么要有专业模式

传统流程里，PM 和 RD 在「需求评审」到「技术方案评审」之间来回多轮，本质是在补**业务流程**和**数据模型**之间的裂缝。等写到代码才发现模型撑不住，就要打回需求重来——这是成本最高的返工。

专业模式把这个裂缝在澄清阶段就摊开：流程和模型是同一个业务现实的两个投影（时间是流程、空间是模型），一条流程本质是模型上的一条路径，所以「模型撑不住流程」可以被精确检查出来，不用等写代码。

## 共同纪律

- **事实自己查**：能自己拿到的一律自己拿——读代码、查线上数据、翻文档。不推测、不问用户。实在无据可依（或深挖成本明显不划算）才问，问时要说明「查了哪几处、查到什么、还差什么」。
- **只澄清不实施**：可以读代码、查数据、画模型、评估方案可行性；禁止写代码、改文件、执行变更。
- **不替用户做取舍**：所有权衡抛给用户拍板。

## 目录结构

```
clarify/
├── SKILL.md                       主流程
├── references/model-protocol.md   模型核对协议（写模型前必读）
├── scripts/build-html.py          渲染 puml → svg，再生成自包含 HTML
└── assets/marked.min.js           HTML 端的 markdown 渲染器
```

## 依赖

- **Java 8+**（跑 plantuml.jar）
- **plantuml.jar**：21MB，不入库。首次跑 `build-html.py` 时自动从 Maven Central 下载
- **无需 graphviz**：`.puml` 里用 `!pragma layout smetana` 走 PlantUML 内置布局引擎
- 不需要 python 第三方库，标准库即可

> 本 skill 自带一份 `build-html.py` 副本，刻意**不依赖** [zele-plan](../zele-plan/)——两个工具各持一份，重复维护换取「单独拿出来就能用」。
