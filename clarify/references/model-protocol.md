# 模型核对协议（专业模式）

本文件是专业模式设计数据模型时的**判据与操作手册**。写模型之前必须读。

---

## 一、为什么要在澄清阶段做这件事

传统流程里，PM 和 RD 在「需求评审」和「技术方案评审」之间来回多轮，本质是在补**业务流程**和**数据模型**之间的裂缝。等写到代码才发现模型撑不住，就要打回需求重来 —— 这是成本最高的返工。

**流程和模型是同一个业务现实的两个投影**：流程是时间维度（状态怎么变），模型是空间维度（什么东西存在）。一条业务流程，本质是模型上的一条路径。

所以「模型撑不住流程」可以被精确地检查出来，不用等到写代码。

---

## 二、概念核对（业务视角）

### 正向：流程 → 模型

把每条流程写成状态转移序列 `S0 --动作--> S1 --动作--> S2`，每个 `Si` 应当是模型的一个合法实例状态。逐一检查六种失配：

| 失配类型 | 表现 |
|---|---|
| **缺实体** | 流程里出现一个业务概念，模型里没有承载它的表 |
| **缺关系** | 两个概念之间有流转/归属，模型里没有这条关系 |
| **缺字段** | 流程要按某维度过滤或判断，但没有这个字段 |
| **基数不符** | 流程假设"一个 X 多个 Y"，模型是 1:1（或反之） |
| **生命周期不符** | 流程假设某状态会变/会被删，模型没地方承载 |
| **写入方缺失** | 某个数据在流程里被产生，但没有字段承接它 |

有任一失配 → 标记 ❌。

### 反向：模型 → 流程

逐个检查模型里的每个**实体、关系、字段**：

> 有没有**任何**一条流程在用它？

没有 → 标记 ⚠️。两种解释，都要抛给用户：

- **模型多余** → 砍掉（避免过度设计）
- **漏了一条流程** → 补上

> 这条反向核对是**免费得到的防过度设计机制**：模型里每一样东西都必须有流程在用它，否则要么砍、要么补。不需要额外立规矩。

## 三、物理核对（技术视角，**必须实测**）

概念上走得通，不等于物理上成立。例如「存 10000 字符并支持筛选」：存得下（TEXT 没问题），但 B-tree 索引单行上限约 2704 字节，10000 个中文字符 UTF-8 是 30000 字节 —— **索引根本建不下**。出路只有 `pg_trgm` GIN、全文检索（语义变了）或放弃筛选，**没有一个是"优化一下"就行的**。

### 五类物理失配与实测方法

| 类型 | 靠什么判 | 怎么实测 |
|---|---|---|
| **存储不成立** | 字段尺寸/形态超出索引或列的能力边界 | 查 `MAX(length(col))`、`percentile_disc(0.99)`、字段类型定义 |
| **查询不成立** | 要求的筛选方式在该量级下走不了索引 | 查真实行数（`reltuples` / `count(*)`）；拿真实 SQL 跑 `EXPLAIN (ANALYZE, BUFFERS)`，看是不是 Seq Scan |
| **基数爆炸** | 关联扇出过大，JOIN / 遍历不可行 | `SELECT avg(cnt), max(cnt) FROM (SELECT count(*) cnt FROM child GROUP BY parent_id) t` |
| **写入不可行** | 写入频率或原子性要求超出单库能力 | 查写入 TPS 量级、是否需要跨表原子 |
| **量级不可持续** | 增长速率下存储/查询会失控 | 日增量 × 保留期 = 稳态规模，再回头看查询是否还成立 |

### 🚫 硬性禁令

**不允许出现"我判断性能可能有问题"这种没跑过的话。**

该查行数就查行数，该跑 `EXPLAIN` 就跑 `EXPLAIN`，该看真实数据分布就抽样看。

原因：AI 一个人扮演 PM 和 RD 两个角色，最大的风险不是"漏了"，而是**推理链内部自洽、但整体有盲区** —— 自己检查自己，永远查不出自己没想到的东西。**唯一能戳破自洽盲区的是实证**：数据和执行计划不会迁就你的推理。

### 物理失配的处置选项

每个物理失配都要给出**明确的几条出路**，抛给用户选，而不是只报问题：

| 出路 | 说明 |
|---|---|
| **换存储** | PG 不行就 ES / 图库 / 列存 —— 但这意味着**技术加成本** |
| **降级需求** | 放弃模糊匹配、降低精度、接受更高延迟 |
| **改流程** | 需求本身变形（如"不做实时筛选，改成离线打标"） |
| **硬上** | 技术接受性能牺牲 |

**这是业务判断，不是技术判断。** 技术能判定"成不成立"（不可行就是不可行），但"接受降级 / 改流程 / 加成本"的取舍必须用户拍板。

同理，概念失配的处置也是业务判断：**改模型还是改流程，取决于业务常识，AI 没资格定。** 例如流程要求"同一订单能同时属于两个用户"——这不是模型不够灵活，是流程设计错了。

## 四、变更后的重跑（分档，避免拖垮澄清）

模型一旦变更，必须重新审视 —— 但要分档，否则每次微调都全量复检，澄清会被拖垮。

| 变更类型 | 举例 | 重跑范围 |
|---|---|---|
| **结构性变更** | 增删实体、增删关系、改基数 | **全量重跑**双向核对 + 物理核对 |
| **字段级变更** | 加字段、改字段名、改长度 | 只复检**涉及该字段**的流程 |

**只要动过，就要重跑，不能跳。** 区别只在范围。

---

## 五、定稿标准

三条**同时**成立，模型才算定好：

1. **概念双向核对无 ❌ 无 ⚠️** —— 每条流程都走得通，每个实体/关系/字段都有流程在用它
2. **每个物理风险点都有结论** —— 要么"当前量级下成立"，要么已明确出路（换存储/降级/改流程/硬上），要么已明确降级
3. **所有取舍都经过用户拍板** —— 没有 AI 自己默默决定的

三条不齐，不许进入收尾。

## 六、产出与讨论

**每一轮模型定稿都要生成 HTML 给用户看**，不是只在最后出一次。模型是讨论的载体。

```
需求迭代/{需求名}/
├── 澄清.md
├── 澄清.html
└── diagrams/
    ├── 用例图.puml / .svg
    ├── 序列图-{流程名}.puml / .svg
    └── 数据模型.puml / .svg
```

```bash
python3 ~/.claude/skills/clarify/scripts/build-html.py "<目录>/澄清.md"
```

抛给用户时，**不要只丢三张图问"行吗"** —— 要把结论结构化地摆出来。

**文档严格三段**（格式见 SKILL.md「输出格式」）：需求摘要 → 三张图 → 需求说明。

第三节**按业务序列逐个展开**，核对结论**归到对应流程的小节里**，不要另立章节。
最后用「待决项汇总」把所有流程里需要拍板的收敛成一张清单：

> | # | 待决事项 | 来自哪条流程 | 需要谁定 |
> |---|---|---|---|
> | 1 | 成员配置不一致时写哪一个 | UC-2 同步配置 | 业务方 |
> | 2 | 10000 字符字段是否放弃模糊匹配 | UC-5 检索 | 业务方 + 技术 |

**用户面对的是具体待决项，不是"帮我看看对不对"，也不是你的查证过程。**
