# zele-plan

给一个需求迭代写技术方案。需求对齐在跑本 skill **之前**已完成，所以本 skill 不做需求澄清，直接从设计开始。

## 两条铁律

### 铁律一：设计必须先穷举，再落笔

**绝不允许写到一半发现"这个设计不对，要换"。** 这不是靠小心，是靠一道硬闸门：

> **闸门**：在写出任何实现细节之前，必须先产出「用例 × 路径穷举表」，并对每条路径做一次反推模拟。
> 反推模拟不通过的，回到穷举阶段重来 —— **此时推倒重来的成本是零，因为还没写文档。**

详见 `references/design-protocol.md`。跳过闸门直接开写 = 违反本 skill。

### 铁律二：非必要不问人

**提问前必须先查。** 如果一个问题在代码、文档、历史方案或互联网里有答案，问出来就是失败。

自查信源优先级：

| 顺序 | 信源 | 怎么查 |
|---|---|---|
| 1 | 本地代码仓库 | `Grep` / `Glob` / `Read`；git 历史 `git log -p -- <file>` |
| 2 | 美团内网代码库 | `meituan-code` skill（`repo` CLI），跨仓库检索 |
| 3 | 学城文档 | `citadel` skill，需求文档原文、上下游设计、接口约定 |
| 4 | 历史技术方案 | `需求迭代/` 下同类需求的既有方案，看别人怎么解的 |
| 5 | 互联网 | `mcp__tavily__tavily_search` / `fetch` skill |

**只有**当问题是"业务意图 / 优先级 / 取舍"这类**代码里根本不存在**的东西，且上述信源都查过时，才允许提问。提问时必须一并给出：**我查了哪几处 → 查到了什么 → 还差什么才能定**。禁止把能查的问题包装成提问。

## 输入

| 输入 | 来源 | 缺失时 |
|---|---|---|
| 需求文档 | `需求迭代/{需求名}/` 下的需求文档 md | 问用户要路径（这属于"确实没有"） |
| 代码仓库 | 当前工作目录，或需求文档里点名的仓库 | 用 `meituan-code` skill 按仓库名定位 |
| 需求名 | 目录名，或需求文档标题 | 从需求文档标题推导 |

**输出目录**：`/Users/huangzele/Documents/obsidian_repo/工程迭代/技术架构知识库/需求迭代/{需求名}/`

产出：

```
需求迭代/{需求名}/
├── 技术方案.md          正文（图用 ![[diagrams/xxx.svg]] 引用）
├── 技术方案.html        单文件自包含，带侧边目录跳转
└── diagrams/
    ├── 用例图.puml       PlantUML 图源
    ├── 用例图.svg        渲染产物（Obsidian 原生可显示）
    └── ...
```

`.puml` 用 PlantUML 写（Obsidian 原生不支持 PlantUML，所以走「渲染成 SVG 再嵌入」这条路，两边都能看）。

## 执行流程

### 阶段 0 · 定位

1. 读需求文档全文
2. 确定代码仓库路径，确认能读到相关模块
3. 若 `需求迭代/{需求名}/` 不存在，创建
4. **读同目录下已有的文件**（原型 HTML、既有需求文档），避免和已有约定打架

### 阶段 1 · 事实采集

把需求里每一句话落到代码上。产出「事实底稿」：

- 涉及的现有模块 / 类 / 表 / 接口，**逐个在代码里确认存在**
- 现有数据模型的实际字段（不是猜的）
- 上下游调用关系（谁调这个功能、它又调谁）

**硬约束：底稿里每条都要能指出来源**（`文件:行号` 或 URL）。凭印象写的断言一律删掉。

### 阶段 2 · 用例与路径穷举（闸门）

按 `references/design-protocol.md` 产出穷举表，包含：

1. **使用方清单** —— 人 + 系统，一个不漏
2. **用例清单** —— 每个使用方用什么功能
3. **路径分解** —— 每个用例拆成正常流 / 分支 / 异常
4. **模型触点** —— 每条路径碰哪些数据
5. **冲突自查** —— 有没有两条路径对同一份数据做了互相矛盾的假设

**完成信号**：能回答"任意一条路径，数据从哪来、到哪去、失败怎么办"，且答案之间不打架。

### 阶段 3 · 设计定稿

1. 数据模型变更 —— 只列本次真正要动的表/字段
2. 逐用例数据流 —— 每个模型在这条路径上"是什么角色"
3. **反推模拟** —— 拿定稿模型把阶段 2 的每条路径走一遍，走不通就回阶段 2

### 阶段 4 · 产出

1. 按 `references/output-format.md` 把图写成 `diagrams/*.puml`（用例图、业务序列图、ER 图）
2. 写 `技术方案.md`，图的位置用 `![[diagrams/xxx.svg]]` 引用
3. 一条命令生成一切：

```bash
python3 ~/.claude/skills/zele-plan/scripts/build-html.py "<输出目录>/技术方案.md"
```

脚本会先渲染所有 `.puml` → `.svg`，再把 SVG 内联进 HTML。**必须跑这一步**，否则 Obsidian 里引用的 SVG 不存在，html 里也是空图。

4. 交付时给出 `技术方案.md`、`技术方案.html`、`diagrams/` 的完整路径

**三个唯一事实源，别搞混**：

| 内容 | 事实源 | 改完之后 |
|---|---|---|
| 正文文字 | `技术方案.md` | 重跑脚本 |
| 图 | `diagrams/*.puml` | 重跑脚本（会自动重渲染） |
| HTML | 生成物 | 永远不要手改 |

**诚实交付**：脚本报「图未找到」或页面上出现黄色/红色提示，说明有图没渲染成功 —— 必须修掉再交付，不要带着坏图交出去。

## 输出结构（务必按此顺序）

```
（开头一段简短需求背景引言，不编号）

1. 用例图            —— 使用方（人+系统）× 功能
2. 业务序列图        —— 每个被改造的用例一张
3. 数据模型 ER 图    —— 只画变更相关的
4. 用例 × 数据流     —— 逐用例讲解模型的数据作用
```

三条必须遵守的排版规则：

- **第 4 节每小节开头先复述对应的业务序列图**，再讲模型的数据作用 —— 图文对照，序列图在第 2 节和第 4 节各出现一次是有意的
- **正文指代数据模型统一用中文名**：首次出现写「风险记录表（`tag_value_risk`）」，之后只写中文。字段名保留英文（那是列名）
- **图全部用 PlantUML**。本 skill 的构建管线只认 PlantUML —— 写了 mermaid 块不会出图，HTML 里只会是一段代码

完整写法、图表语法、代码节制规则见 `references/output-format.md`。

---

## 红线

- **业务序列图的执行者只能是人或外部系统**，禁止画成 Controller → Service → DAO 这种模块间调用
- **不写大量代码**。数据模型用 ER 图 + 文字表达，不要甩建表 SQL
- **不写没穷举完的方案**。闸门没过就继续查，不要"先写着看"
- **不编造**。字段名、表名、接口名必须在代码里核实过
