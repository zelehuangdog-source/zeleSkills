# 需求澄清器

用户即将开始一个复杂任务，你需要在动手之前系统性地收集需求细节。使用 AskUserQuestion 工具把所有有歧义、有二义性、不确定的地方全部问清楚，直到需求毫无模糊空间为止。

> **🔥 不限定问题数量**：有任何疑问都要问，不要为了"少问"而放过模糊点。
> - AskUserQuestion 单次最多放 4 个问题，这只是工具上限，**不是澄清的上限**。
> - 一轮问完后若还有未澄清的点，**继续发起下一轮 AskUserQuestion**，多轮提问直到没有任何歧义。
> - 宁可多问，不可漏问；确保需求没有歧义、没有二义性。

> **🔥 边界（最高优先级，禁止越界）**：
> 本 skill **只做澄清，不做计划，不做实施**。
> - **禁止**给出实现方案、技术选型、架构设计、步骤拆解（那是 plan 的事）。
> - **禁止**写任何代码、改任何文件、跑任何命令（那是实施的事）。
> - 收齐答案后，输出一段需求摘要，然后**通过 AskUserQuestion 选择器让用户选下一步**（计划 or 直接实施），不要只打文字让用户自己打字。

## 规则

1. 分析用户输入（通过 $ARGUMENTS 传入）。澄清分两层，**先专属、后通用**：
   - **第一层 · 任务专属决策点（先做）**：从这件事本身出发，拆出它特有的**决策分叉**——即完成这个任务天然要在哪些地方做二选一 / 多选一的决定（例如"规则作用在调用边还是节点""单向还是双向匹配""命中后拦截还是告警"）。这些点最贴合当前任务、也最容易被通用清单漏掉，**优先**把它们变成问题。
   - **第二层 · 固定维度兜底（再做）**：在专属决策点之外，用第 2 步的固定维度清单查漏补缺。**固定维度是安全网、不是全部**——它保证不漏大类，但不替代第一层的任务专属决策点。
   - **提问前先过滤「事实 vs 决策」**：对上面两层筛出的每个待澄清点，先分类再决定问不问——
     - **事实**（代码里有客观答案，如某字段现在的类型、某方法现在的调用方、当前用的枚举 / 配置）：**你自己 grep / 读代码去查，不要拿来问用户**。
     - **决策**（代码里没有答案、只能由用户拍板，如是否拦截、范围做到哪、异常分支怎么处理）：才放进 AskUserQuestion 问用户。
     - **限定**：只查廉价、明确能查到的事实；若某事实要深挖很久才能确认，直接问用户更快。查代码只为查事实，**不得滑向实施**（"只澄清、不实施"的越界红线仍在）。
2. **承接第二层**，遍历以下固定维度做兜底查漏，凡是存在不确定/歧义的维度都要提问（不限数量，单轮超过 4 个就分多轮问）：
   - **范围**：做到什么程度？哪些包含、哪些排除？
   - **优先级**：性能优先、可读性优先、还是开发速度优先？
   - **约束**：有什么技术限制、时间限制、兼容性要求？
   - **验收标准**：怎么算做完了？需要测试吗？
   - **影响范围**：允许改动哪些模块？是否可以改公共代码？
   - **风格偏好**：命名、结构、模式有倾向吗？
   - **边界/异常场景**：空值、极值、并发、超时、幂等、重复提交、数据不存在、权限不足、网络失败等异常分支怎么处理？
3. 每个问题提供 2-4 个选项，选项要覆盖常见选择，且每个选项都要**附简短权衡说明**（选它意味着什么、有什么代价），让用户在信息充分的前提下选，而不是面对一排干巴巴的选项自己从零判断。
   - **有合理默认值 / 最佳实践的问题**：把你推荐的答案放在**第一个**，label 后标注「（推荐）」，并在 description 里说清推荐理由。让用户在你的判断上确认或推翻，而非冷启动。
   - **纯偏好、无客观优劣的问题**（如范围做到哪、是否允许改公共代码、命名风格倾向）：**不要强行标「（推荐）」**——这类题没有客观最优解，硬推会误导用户或显得替用户拿主意。只平铺选项、各自附权衡说明即可。
4. **同一批（同一次 AskUserQuestion）里只放互相独立的问题**：问题之间不要重叠，每个问题覆盖独立维度，且彼此**没有依赖关系**——即任何一个问题的答案都不会改变「另一个问题要不要问 / 怎么问 / 选项是什么」。
   - **判断依赖**：如果「Q_B 问什么、给哪些选项」取决于「Q_A 怎么答」，那 Q_B 就依赖 Q_A，二者不能放进同一批。
   - **有依赖就拆到后续轮次串行**：先在本轮问前置问题（Q_A），拿到答案后，再在下一轮根据答案追问依赖它的问题（Q_B）。宁可多分一轮，也不要把有依赖的问题塞进同一批导致选项给错。
   - **保持轻量**：只对明显的依赖做拆分，不要为了分析依赖而对每个问题过度纠结——澄清的命根子是快和广。
5. **🔥 显式提出边界情况（必做）**：除了澄清用户已经说出来的需求，还要**主动设想用户没说但实际会遇到的边界 case**，把它们以问题形式抛出来，和用户一起摸清边界。
   - 思考维度：输入边界（空、null、超长、特殊字符、负数、零）、状态边界（首次/重复、存在/不存在、已删除/已禁用）、并发边界（并发写、重复请求、幂等性）、依赖边界（外部服务超时/失败/降级）、数据边界（数据量大、跨租户、历史脏数据）、权限边界（无权限、越权访问）。
   - 目的：**既帮用户想到他没考虑过的场景，也帮自己提前对齐异常分支的处理方式**，避免实施阶段才发现歧义。
   - 形式：把发现的边界 case 作为 AskUserQuestion 的问题项，给出 2-4 个常见处理选项（如"抛异常 / 静默忽略 / 返回默认值 / 走兜底逻辑"）。
6. 每轮答案收齐后，检查是否还有遗留歧义；若有，继续发起下一轮提问，直到全部澄清
7. 确认无任何歧义后，输出一段简短的需求摘要，然后**使用 AskUserQuestion 让用户选择下一步动作**（不要只打一行文字让用户自己打字）：
   - 问题示例："需求已澄清完毕，下一步怎么做？"
   - 选项：「进入计划模式」（制定实施方案后再动手）、「直接实施」（需求清晰，直接开始编码）
   - 用户也可以通过自动提供的 "Other" 输入框给出其他指令
8. 根据用户选择执行对应动作：选「进入计划模式」则调用 EnterPlanMode；选「直接实施」则直接开始编码；选 Other 则按用户输入执行

$ARGUMENTS
