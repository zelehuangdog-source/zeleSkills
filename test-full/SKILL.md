# test-full · 全方位测试（后端为主，可选前后端联调）

写完后端后，手动喊我对本次改动做一次全方位测试：穷举代码分支、覆盖各中间流程字段为 null 的 case，走真实链路（调用本地服务接口）验证行为。

> **仅手动触发**（`/test-full`）。不自动触发。

**五条贯穿全程的硬性要求**：

1. **服务没起就派子 agent 用 `start-backend` 起**，不要自己手敲 mvn，也不要把编译日志灌进主上下文。
2. **执行前必须先产出用例清单 HTML 给用户看**（内容见第五步）。**用例设计不设确认卡点** —— 生成完、打开完就继续往下跑，不等用户回复（唯一会停下来问用户的是硬性要求 5 的可执行性卡点）。
3. **所有接口调用一律异步触发，不同步阻塞等待**。你只负责生成脚本 + 后台拉起 + 收结果文件（见第七步）。
4. **测出的问题只报告、不修**。这个 skill 的职责边界是「验证 + 报告」，**严禁顺手改业务代码去修 bug**，哪怕看起来只是改一行、哪怕你很确定怎么改。**前端代码同样不改**（联调阶段测出的前端 bug 也只进表格）。所有发现的问题以**表格**形式在对话里反馈给用户，由用户决定改不改、怎么改。
   - 唯一允许写的代码是**测试驱动用的后门接口**（第三步的 TestController/BackdoorService）、**测试数据**（第六步的 INSERT）、**联调用的前端 dev server 代理配置**（只改「指向哪个后端」这种环境配置，不改业务逻辑），这三类不算「修 bug」。
   - 如果用户看完表格后明确说「改吧」，那是下一轮的事，不在本 skill 范围内。
5. **「环境不通」永远不是跳过用例的理由** —— 用例一旦列进 `cases.html`，就必须跑完。
   - 拉起脚本前先做**全量可执行性预检**（第七步 7.0）：逐条确认入口可达、鉴权可过、入参可造、判定依据可得。**每条用例只有两种合法状态：预检通过，或经用户明确接受跳过** —— 还有卡在中间的就先问用户，问完再拉起脚本。
   - 任何一条跑不了（服务起不来、接口要鉴权、test 库连不上、前端没实现、外部依赖不可用……），**必须先自查**（配置/端口/连接串/token/日志/降级路径），自查无解就把全部不可执行项**一次性**摆给用户，只给两个出口：**用户给方案**（拿到后解决 → 重跑预检 → 全量跑完）或**用户明确接受跳过**（才可在 HTML 里标 `跳过-用户确认`）。
   - **严禁**：自己判断某类环境不通就把用例划掉、写成「先不跑这些」「不适用」、假装跑过了，或把失败悄悄吞掉。**没有用户确认记录的跳过 = 违规**。
   - 硬性要求 2 说的是用例设计不设确认卡点；**可执行性**是硬卡点（7.0），这一条不打折。

## 零、选择测试强度（先做，不设默认）

**第一步用 `AskUserQuestion` 让用户选测试强度**，不要替用户设默认、也不要自行揣测：

- 问题：本次测试做多重？
- 三个选项：
  - **轻度（只测主流程）** —— happy path + 1~2 条最明显错误路径（必填缺失、数据不存在）。冒烟：链路跑得通吗。
  - **中等（推荐日常默认）** —— 覆盖每个对外入口方法体里的**所有一级分支**（`if/else`、`switch`、早返回），但不深挖被调方法内部的嵌套分支；只测**关键 null**（入参级、外部依赖/DB 返回 null）和**常见输入边界**（空集合、空串、非法值各一发）。
  - **重度（全方位）** —— 穷举所有分支含深层嵌套 null、全输入边界矩阵。适合核心/高风险逻辑或上线前把关。

强度只影响**第四步的用例范围**，其余步骤三档一致。数据准备与强度无关——任何档位都是「缺数据就造」。HTML 和总结开头都要注明本次用的是哪一档。

- **同一次 `AskUserQuestion` 里追加第二问**：是否需要覆盖高并发 / 大数据量场景？
  - **不需要** —— 只跑功能用例（默认）。
  - **需要** —— 追加设计一批压力向用例：单独产出 `stress-cases.html`（与普通用例 HTML 隔开）、单独的执行脚本，**默认不执行**，用户明确确认后才跑（设计规范与卡点见 4.5 节）。

- **同一次 `AskUserQuestion` 里追加第三问**：是否需要做前后端联调？**三档单问**（不要额外追问前端状态，档位自带降级语义）：
  - **不做** —— 只验后端（默认）。
  - **仅契约核对** —— 只做 A 层：拿第七步抓到的真实响应体 diff 前端 TS 类型 / 字段引用 / 可空性假设。**不需要前端跑起来**，前端还没实现或 dev server 没起时选这档。
  - **完整端到端** —— A 契约核对 + B 端到端行为（数据断言 + 交互断言）+ C 组件级截图样式核对。需要前端 dev server 已在跑且代理指向本地后端。

  选后两档的，按 **4.6 节**设计并执行联调用例。若执行时发现前置条件不满足（前端未实现、dev server 起不来、代理没指本地后端），**按 7.0 当不可执行项一次性问用户**（给方案打通 / 明确接受降档）；用户确认后才降档，并在 `integration-cases.html` 页头和最终总结里写明实际做到了哪一档。不要静默降档、不要假装跑过了。

## 一、确认服务在跑（没起 → 子 agent 调 start-backend）

1. **先探活**：从项目配置（`application-*.yml` / `bootstrap.yml`）拿端口，用 `lsof -i :{port} -sTCP:LISTEN` 或 curl 健康检查确认服务是否已在跑；也可参考本地日志 `/tmp/{项目名}-dev.log` 的尾部判断状态。
2. **没起 → 派子 agent 启动，不要在主流程里自己启**：

   ```
   Agent(
     subagent_type: "general-purpose",
     description: "启动后端服务",
     prompt: "用 Skill 工具调用 start-backend skill 启动 {项目名}（路径 {项目绝对路径}）。
              全程不要把编译日志、启动日志正文回传给我。
              最终只回报三行：1) 是否启动成功 2) 监听端口 3) 失败时的根因一句话 + 日志文件路径。"
   )
   ```

   - **必须走子 agent**：编译 + Spring 启动日志动辄上千行，放主上下文会把用例设计挤掉。子 agent 只回报「起没起来 + 端口」。
   - **子 agent 后台跑，你别干等** —— 派完立刻继续做第二～六步（锁范围、读码、设计用例、出 HTML、备数据）。这些都不依赖服务在跑。
   - **卡点在第七步之前**：真正要发请求前，必须已收到子 agent 的成功回报。若回报失败，走「阻塞处理」。
3. 服务已在跑，则跳过本步，记下端口继续。

## 二、确定测试范围

**范围识别优先级**：

1. **对话历史为主** —— 本次会话里刚写/刚讨论/刚改的代码，就是要测的目标。先从对话上下文锁定改了哪些类、方法、接口。
2. **git diff 为辅** —— 用 `git diff` / 最近提交做补充和交叉校验，补上对话里没显式提到但一起改动的上下游。

把「本次改动 + 其直接上下游」列成待测清单，再往下走。

## 三、发现接口入口

测试通过**调用本地运行的服务接口**（HTTP/RPC）驱动，先找到能打的入口：

1. 从改动的 Controller / 接口推断入口，确定 URL、方法、入参结构、鉴权要求。
2. **若改动的代码没有可直接调用的入口**（如只改了 DomainService / Repository 内部方法）：
   - 允许**写一个后门接口到对应的 TestController 类**，把要测的方法暴露出来方便驱动。
   - 位置遵循分层规范：`starter/controller/test/{业务模块}/XxxTestController.java`，复杂逻辑下沉到 `application/backdoor/{业务模块}/XxxBackdoorService.java`，TestController 只做接收/校验/调用/返回。
   - **这些后门代码测完保留**，作为可复用后门。测完在总结里列出新增了哪些后门接口。
   - ⚠️ 新增后门代码后**服务需要重启才生效** —— 同样派子 agent 走 `start-backend`（见第一步），不要自己在主流程编译。

## 四、分析分支 → 用例矩阵（按所选强度收放）

读改动涉及的源码，按第零步选的档位设计用例。每条用例必须明确四要素，后面第五步的 HTML 直接由它渲染：

| 要素 | 说明 |
|------|------|
| **做什么** | 一句话描述场景 + 命中的具体分支（带 `file:line`） |
| **依赖什么** | 前置数据（哪张表哪行）、依赖的前序用例、外部服务状态 |
| **怎样算通过** | 具体的判定条件：返回体哪个字段等于什么、DB 哪张表哪行变成什么状态。**不许只写「返回 200」** |
| **入参** | 完整可复现的请求体 / query |

**设计时就把「本环境真能跑」想清楚** —— 依赖外部服务/中间件的场景，先定好怎么让它可控（后门、mock、指向线下实例、用造数构造状态），别只写「依赖 X 服务」然后指望跑的时候正好通。确实只能靠真实外部依赖、当前环境打不通的场景，也要**写成用例**、连同降级路径一起留到 7.0 预检摆给用户（硬性要求 5），**不许在设计阶段就自己划掉**。

**轻度**：只覆盖主流程 happy path + 1~2 条最明显的错误路径（必填缺失、数据不存在）。

**中等**：
- 覆盖每个对外入口方法体里的**所有一级分支**：`if/else`、`switch`、三元、`Optional`、早返回、循环进入/不进入。**不深挖被调用方法内部的嵌套分支**。
- **关键 null**：入参级 null、外部依赖/DB 返回 null。不穷举每个中间字段的 null 组合。
- **常见输入边界**：空集合、空串、非法值各一发。
- 状态边界：数据存在/不存在这类高频状态。

**重度**：
- **穷举所有分支**：每个 `if/else`、`switch`、三元、`Optional`、循环进入/不进入。
- **每个中间流程字段为 null 的 case** —— 逐层追进被调用的方法，凡是中间过程某个字段/对象可能为 null 的分支都要覆盖。
- 全输入边界矩阵：空集合、空串、超长、特殊字符、负数、零、极值。
- 全状态边界：存在/不存在、已删除/已禁用、首次/重复。
- 依赖边界：外部服务/DB 超时、失败、返回空。

## 4.5、高并发 / 大数据量用例（仅当第零步用户勾选「需要」才做）

普通功能用例之外单独设计一批**压力向用例**，与普通用例完全隔离（独立 HTML、独立脚本、独立结果文件、独立执行卡点）。

**用例设计维度**（按本次改动入口的具体形态裁剪，不硬凑）：

- **高并发**：N 个并发同时打同一接口（脚本里 `&` 并发 curl 或 `xargs -P`），覆盖：
  - 并发写同一行 / 并发创建同类资源（唯一键冲突、覆盖丢失）
  - 重复提交 / 幂等性（同一请求并发发两次）
  - 计数原子性（如任务计数、库存类字段并发自增是否不丢不穿）
  - 通过标准**必须包含 DB 终态核对**（行数、唯一键无冲突、计数与明细实际一致），只看 HTTP 200 不算通过
- **大数据量**：贴近上限的入参与大结果集，覆盖：
  - 批量接口打满上限值（如单次上限 MAX_BATCH_SIZE 条）+ 上限 +1（应被校验拦截）
  - 大结果集分页正确性（总数、首尾页边界）
  - 通过标准包含**耗时记录** + DB 落库行数核对（耗时明显劣化也要进问题表，即使功能正确）
- 并发度 / 数据量按「接口真实上限 + 适度超配」设计，在 HTML 里写明为什么是这个量级。

**隔离与卡点（与普通用例的关键差异）**：

- 单独产出 **`stress-cases.html`**（与 `cases.html` 同目录并列），结构与 5.2 一致，页头额外注明「⚠️ 压力向 · 默认不执行」，并列出预计造数据量与执行影响（写多少行、打多久、会不会影响共享 test 环境他人使用）。
- 单独生成 **`run-stress-cases.sh`**，结果落 **`results-stress.jsonl`**、响应体落 **`responses-stress/`**，与普通结果文件分开。
- **默认不执行**：HTML 生成并 `open` 后，**用 `AskUserQuestion` 问用户是否执行**（选项：立即执行 / 暂不执行）。用户明确选「立即执行」才拉起脚本；选「暂不执行」则跳过（这是**用户自己**的决定，属合法跳过，`stress-cases.html` 标注「用户暂缓执行」并保持全部「待执行」，后续用户随时可喊补跑）。
- **用户选了「立即执行」就别再打折**：压力向用例执行前同样走 7.0 预检，脚本同样做结果条数对账与 `INCOMPLETE` 检查；跑不完一样要查原因补齐，或经用户明确接受才可标跳过。
- 造数可能量大（如批量插几千行），执行前先造数、并在 HTML 造数清单里列出实际行数与标记。

## 4.6、前后端联调用例（仅当第零步勾选后两档时做）

### 4.6.1 先查前置条件，不满足按 7.0 问用户（不要硬造用例、不要静默降档）

端到端要四样齐，缺哪样降哪档：

| 前置条件 | 怎么查 | 缺了怎么办 |
|---------|-------|-----------|
| 前端仓库 / 工作区 | 见下方映射表；推不出来就**一次性问用户**（仓库路径 + 分支/工作区） | 阻塞：问用户 |
| 前端已实现该需求 | fe 仓库 `git log --oneline -20` / `git status` 看本次需求改动；或 grep 后端接口 URL | 按 7.0 当**不可执行项**问用户：给方案打通端到端 / 用户明确接受降档。接受后 B/C 才可标「前端未实现，用户确认跳过」 |
| 前端 dev server 在跑 | 端口从 `vite.config.ts` / `package.json` 的 scripts 拿，再 `lsof -i :{fePort} -sTCP:LISTEN` | 后台拉起 `pnpm dev` / `npm run dev`（`run_in_background: true`），记下端口 |
| dev server 代理指向本地后端 | 读 `vite.config.ts` 的 `server.proxy`，确认 target 是 `localhost:{后端端口}` | **阻塞项**：代理没指本地后端 = 测的是远端，联调结果无意义。改代理配置（属环境配置，允许改）或问用户 |

> **降档不是你自己能拍板的事**：第零步选了「完整端到端」但前置条件不满足时，把缺的项按 7.0 摆给用户（给方案 / 明确接受降档），**不要静默降档**，也不要用「环境不通」把 B/C 这笔账糊过去。

### 4.6.2 联调用例的锚点是「契约变更点」，不是后端用例清单

**禁止把后端用例逐条映射成联调用例** —— 后端用例大半是内部逻辑分支（null 兜底、边界值、异常分支），前端压根不消费，映射过去就是噪音，用例表和执行时间都会膨胀。

正确链路：

```
后端本次测试范围（第二步锁定的改动）
  → 抽出「对外契约变更点」
  → 在 fe 仓库 grep 前端是否真的消费了这个点
  → 才生成联调用例
```

**契约变更点清单**（有哪类抽哪类）：

- 新增 / 删除 / 改名的接口（URL、method）
- 请求字段增删改、必填性变化
- 响应字段增删改、类型变化、**可空性变化**（原来必返回、现在可能返回 null）
- 枚举新增值 / 改值
- 错误码新增或语义变化
- 分页 / 排序语义变化
- 字段语义变化（如原来的 `title` 现在装的是 `name`）

**前端消费点怎么找**：在 fe 仓库 grep 接口 URL 片段、hook 名（`useXxx`）、字段名。
- 命中 → 生成联调用例，记下 `文件:行`
- 没命中 → 在 HTML 里列一行「不涉及前端」，**写明 grep 了什么、确认没搜到**，不许静默跳过

### 4.6.3 三层用例（按验证手段分层，来源当标签）

按来源分「回归 / 新增」看着自然，但这两类在联调里**执行手段完全一样**，分两张表只会重复。所以按验证手段分三层，把来源当标签打在用例上：

**A 层 · 契约一致性核对（免浏览器，零成本，ROI 最高）**

- 手段：拿第七步已抓到的 `responses/{caseId}.json` 真实响应体，对照前端 TS 类型定义 / 字段引用 / 可空性假设做机械 diff。
- 查什么：前端声明了但后端没返回的字段、后端返回了但前端没声明的字段、枚举值前端少判了、**前端按非空用（`data.xxx.yyy`）但后端可能返回 null**、字段名拼写不一致、类型不一致（后端 string 前端 number）。
- 这层**全量做，与强度档位无关** —— 它不花时间。

**B 层 · 端到端行为验证（需要浏览器）**

断言分两类，**两类都要有** —— 只做数据断言会漏掉全部交互问题（点了没反应、状态没同步、按钮不禁用）：

**B1 数据断言** —— 页面渲染出来的值 == 后端 `responses/*.json` 里的值。

- 手段：ego-browser 打开前端真实页面 → 触发后端真实请求 → 取 DOM 文本/属性与响应体逐字段比。
- 通过标准必须是**具体渲染值**（DOM 文本 / 属性 == 期望字符串）+ 无控制台报错 + 无失败网络请求。**不许只写「页面能打开」「没报错」。**

**B2 交互断言** —— `动作 → UI 状态`。这是「动作合理」的落点，**没有它交互行为就没人负责**（数据断言管不到、静态截图也看不出来）。

- 手段：ego-browser 做动作，再用可观测条件断言状态变化：
  - 元素出现/消失：`waitForSelector`，或 `page.evaluate(() => !document.querySelector(...))`
  - 属性变化：`page.evaluate` 读 `disabled` / `aria-expanded` / class
  - URL 同步：读 `location.search`（筛选、分页、Tab 状态上 URL 的项目必查）
  - 请求发出：`page.on("request")` 或 CDP，断言条数与关键参数
- 至少覆盖本次改动涉及的这些动作，**有哪个查哪个，不硬凑**：

  | 动作 | 期望状态 |
  |------|---------|
  | 筛选 / 搜索 / 排序 | 列表内容变了、URL query 同步、翻页重置到第 1 页 |
  | 分页 | 页码与总数正确、首尾页边界 |
  | 提交 / 保存 | 期间按钮 disabled + loading，结束后恢复；成功后列表刷新或出 toast |
  | 二次确认 / 危险操作 | 弹确认框；取消不生效 |
  | 表单校验 | 非法输入出提示、按钮不可提交 |
  | 展开 / 收起 / Tab 切换 | 状态保持或按预期重置 |
  | 空数据 / 请求失败 | 出空态或错误态，而不是白屏 / 一直 loading |

- 通过标准同样要写**具体状态**（`button[disabled]` 存在、`?level=high` 出现在 URL、出现「暂无数据」文案），**不许只写「点击正常」。**

- 来源标签（B1/B2 通用）：
  - `回归` —— 后端改动了老接口/老字段，前端**老页面**是否还正常
  - `新增` —— 前端本次**新写的页面 / hook / 组件**，接后端真实数据与交互是否正确

**C 层 · 样式核对（截图，是 checklist 不是 case）**

- 手段：ego-browser 截图落盘 → 主 agent 用 Read 工具**逐张看图**再下结论。**不要只看截图文件存在就判通过。**
- 单独出 `style-checklist.html`，不进用例表（它没有自动 pass/fail）。

**基准（决定「合理」是拿什么比的）**，按优先级取：

1. **需求目录的原型 HTML** —— 宽松匹配需求文档同级及子目录下的 `原型*.html` / `增量原型*.html` / `方案与原型*.html` / `ui-prototype*.html`。有就优先用，并写清对照的是第几屏。
2. **同模块既有页面** —— 原型缺失时，截图同模块老页面做观感对照。
3. **项目 `CLAUDE.md` / 样式 token 文件** —— 颜色、间距是否用 CSS Variables 而非硬编码。

**粒度必须落到「前端增量代码」，不是「页面」**：

- 先 `git diff --name-only`（对照本次需求的分支/工作区）拿到改动的组件文件清单。
- **逐个组件出核对项**，新增的小组件（新 Tag、新 Tooltip、新状态徽标、新空态插画）也要有自己的一张**局部截图**，不能用整页缩略图糊过去。
- 整页截图只用来判「布局没塌/没重叠」，细节一律看局部截图。

**截图覆盖三态**：默认态 + 空态/错误态 + 长内容态（用第六步造的数据触发超长文本、超长枚举值、多行）。长页面的关键区域**单独截** —— 整页长图 Read 进来会被压缩，细节看不清。

**核对维度**（按本次改动裁剪，不硬凑）：布局没塌/没重叠、长文本与超长枚举值不溢出、空态/加载态/错误态三态齐全且文案中文、数字与日期格式一致、颜色间距用 CSS Variables 而非硬编码、与基准及同模块既有页面观感一致。

**反走过场（硬约束，不遵守等于没做 C 层）**：

- 每条核对项**必须写依据**：「对照了 `原型-XXX.html` 第 2 屏」「对照了同模块 `YyyPage.tsx` 的卡片样式」。**只写「符合」不算。**
- **全项「符合」但零佐证 → 整体标「未核对」，不算通过。**
- 不符合项**必须能对应到截图**（指明哪张、哪个区域），不许写「样式有问题」这种无指向结论。

### 4.6.4 执行方式：主 agent 直接用 ego-browser 跑

- **拿 API**：先 `Read ~/.claude/skills/ego-browser/SKILL.md`。它在 `settings.json` 里是 `user-invocable-only`，**Skill 工具调不起来**，但 CLI 能直接用，读文档即可。
- **跑法**：Bash 里 heredoc —— `ego-browser nodejs <<'EOF' ... EOF`。heredoc 跑的是 Node.js，页面内的代码要放进 `page.evaluate()`。
- **一个 TaskSpace 贯穿整场联调**：第一次 `taskSpace("{需求名}联调")` 后 print `spaceId`，后续轮次 `taskSpace({spaceId})` 恢复，**不要每轮新建**（也不要为恢复卡住的页面新建）。
- **断言写在 heredoc 里，只 print 一行结论 JSON**：

  ```js
  console.log(JSON.stringify({ caseId: "I03", pass: true, expect: "高风险", actual: "高风险" }));
  ```

  **严禁 print `snapshot()` 全文 / 整页 HTML / 完整响应体** —— 那是几万 token，会把主上下文挤爆。要细节就落盘，需要时再定向 Read。
- **每条断言同时 append 一行到 `integration/results-integration.jsonl`**（heredoc 内 `await import("node:fs/promises")` 写），字段至少 `{"caseId","layer":"A|B1|B2","pass","expect","actual","screenshot"}`；**断言失败/脚本抛错也必须写一行**，不允许静默吞掉。
- **截图落盘**：`await page.screenshot({ path: "{产物目录}/integration/screenshots/{caseId}.png" })`，再用 Read 看图。
- **登录态**：ego-browser 接用户真实浏览器，内网站点 SSO 免登可直接用 —— 这正是选它的理由。真遇到要手输登录的页面，用 `task.handOff()` 交给用户点，别自己猜。
- **不要用固定 `waitForTimeout` 碰运气**，用 `waitForSelector` / `waitForFunction` 等可观测条件。
- **B 层是交互式跑**（每轮看页面状态再决定下一步），**不走第七步那种一次性后台脚本**；A 层是纯读码分析，C 层可以一个 heredoc 批量截完所有页面（但核对结论要逐张 Read 看图后写）。

### 4.6.5 失败与降级

- 前置条件不满足 → **先按 7.0 问用户**（给方案打通 / 明确接受降档），确认后才降档，并写进 `integration-cases.html` 页头和最终总结（本次只做了 A 层 / 经用户确认 B 层跳过 N 条），不要静默降档、不要假装跑过了。
- 联调测出的问题**同样只报告不修**（硬性要求 4）—— 前端代码也不改。
- B 层某条失败，**先归因再进表**：看该用例对应的后端请求在 `results.jsonl` 里过没过。
  - 后端过、前端渲染错 → 前端问题
  - 后端本身就错 → 后端问题（已在问题表里，**不要重复列**）
  - **归因结果必须写进问题表的「代码位置」列**（前端 `Xxx.tsx:42` 还是后端 `Xxx.java:88`）。

## 七、异步执行（只触发，不阻塞）

### 7.0 执行前可执行性预检（硬卡点，先做）

**用例列进 `cases.html` 就等于承诺会跑完。** 拉起脚本之前，逐条确认每条用例都跑得动——**不是**等服务起没起，而是逐条核验下面的项，缺哪项就当场补齐：

| 核验项 | 怎么确认 | 不过怎么办 |
|-------|---------|-----------|
| **入口可达** | 用例的 method + path 在服务里真实存在：读 Controller 映射确认，或对**只读**接口发一次探测 curl 看是否 404 | 路径写错就改；入口不存在 → 按第三步补后门（需重启服务，走子 agent） |
| **鉴权可过** | 对比服务 SSO 配置的 `sso.excludedUriList`，确认该路径免鉴权；不免鉴权的要有 token/登录态 | 免鉴权清单外的接口：换等价豁免路径（如 `/test/**` 后门）、拿 token，或按下面「不可执行项」问用户 |
| **入参可造** | 用例依赖的前置数据（哪张表哪行）已存在或已按第六步造好；依赖的前序用例在脚本里排在其前面 | 补造数、补依赖顺序 |
| **判定依据可得** | 需要 DB 核对的用例：先跑一条只读探测（如 `select 1`）确认 test 库连得通、核对 SQL 语法可跑 | 连不上库 → 按第九步找连接串；找不到问用户 |
| **写操作不撞车** | 写用例的目标行/唯一键不会被现存数据顶掉（唯一键冲突、状态机不允许） | 换唯一值、清场或改用带标记的新行 |
| **外部依赖可用** | 用例依赖的外部服务/中间件可达；不可达时先找降级路径（指向线下实例、mock、后门） | **不要直接判「跑不了」**，先穷尽降级路径，仍不行才进「不可执行项」 |

预检结果落 **`cases-preflight.md`**（与 `cases.html` 同目录），每条用例一行：用例ID | 可执行/不可执行 | 卡在哪一项 | 解决方案 / 缺什么信息。跑完回填后仍保留该文件。

**不可执行项的唯一出口**：用 `AskUserQuestion` 把全部不可执行项**一次性**摆给用户（合并成一个问题，逐条列出用例ID + 卡点 + 你试过哪些方案 + 你建议的解法），选项固定两个：

- **我提供方案** —— 用户给端口/token/连接串/前端仓库/环境信息等。拿到后解决 → **重跑预检** → 剩余用例全绿才拉起脚本。用户给方案后仍跑不通的，再问一轮，不要自己拍板跳过。
- **明确接受跳过** —— 用户确认这些用例本次不跑。此时才可在 `cases.html` 状态列写 `跳过-用户确认`，并在最终总结里单独列出清单。

**没有第三条路**：不许自己标跳过、不许写「环境不通/先不跑这些」、不许把跑不了包装成「不适用」或「弱化断言凑通过」。

### 7.1 生成 `run-cases.sh`

- **独立用例并发**：无数据依赖的用例用 `&` 并发拉起，末尾 `wait`。
- **依赖链串行**：造数 → 依赖该数据的用例，或写同一行、有先后因果的，必须按顺序串行。先做依赖分析再分组。
- **不要给 curl 设超时**（别加 `--max-time`）：有些接口本来就跑得久（大批量刷数、图计算、同步任务），砍掉是误判成失败。脚本是后台异步跑的，跑多久都不阻塞你，让它跑完。
- **每条用例把结果 append 到 `results.jsonl`**，一行一个 JSON，字段至少包含：

  ```json
  {"caseId":"C01","name":"...","httpStatus":200,"costMs":153,"ok":true,"error":null,"bodyFile":"responses/C01.json"}
  ```

  - curl 本身失败（连不上、超时）也要写一行，`error` 记录原因，**不允许静默吞掉**。
  - 完整响应体单独落 `responses/{caseId}.json`，不要塞进 jsonl。
- **脚本末尾必须自证跑完**：统计 `results.jsonl` 行数（含失败行）与用例条数对账，全齐打 `ALL_DONE expected=N actual=N`；有缺席打 `INCOMPLETE expected=N actual=M missing={caseId,...}`。
  - **看到 `INCOMPLETE` 就是「用例没跑完」**，必须查清缺的那些为什么没落结果（curl 挂掉、脚本中途退出、依赖用例失败导致后续没触发、分组写漏），修好重跑补齐。**不许拿 M 条的结论当 N 条的结论汇报，也不许把缺席的解释成环境问题收尾。**
  - 每一条例外（跑不了、被跳过）同样要落一行 `ok:false` + `error`，静默缺席会被这条对账抓出来。

### 7.2 后台拉起，同时干别的

用 Bash 工具的 `run_in_background: true` 触发脚本：

```
Bash(command: "bash {产物目录}/run-cases.sh > {产物目录}/run.log 2>&1",
     run_in_background: true)
```

- 拉起后**立刻去做别的事**：继续读源码推导各用例预期、准备 DB 副作用核对 SQL。不要空转轮询。
- 脚本跑完会有 task 通知，届时再读 `results.jsonl`。
- 用例数很多、想看实时进展时，可用 `Monitor` 盯 `results.jsonl` 里的失败行（filter 要同时匹配成功与失败信号，别只匹配 happy path）。

## 八、判定与回填

- **先对账再判定**：看到 `INCOMPLETE` 一律先补齐重跑，**不许带着缺席行进入判定**；「跑不完就按跑了的汇报」是本 skill 明令禁止的收尾方式。
- **依代码逻辑自行推导预期并判定** —— 读源码推导每个用例的预期返回值 / 副作用，对比 `results.jsonl` + `responses/` 实际结果，判定通过/失败。
- **判定要具体**：不只看 HTTP 200，要校验返回体字段；有 DB 副作用的用例必须直连 test 库核对。
- **回填 HTML**：重写 `cases.html`，给用例表补上「实际结果」「通过/失败」两列，失败行标红并附 `file:line` + 疑似原因。页头加一行汇总（通过 X / 失败 Y / 跳过-用户确认 Z）。
  - 跳过列的每一行都必须能对应到 7.0 预检时用户的明确接受；对话里拿不出这条确认记录的，说明流程被违规执行了，回去问用户，不要保留静默跳过。
- **判完就停手，不要动业务代码**（见开头硬性要求 4）。定位到根因也只是写进问题表，不改。

### 8.1 联调回填（仅勾选联调后两档时）

- **顺序：A 层先做（纯读码，快），再跑 B 层** —— A 层查出的可空性变化、枚举漏值、字段名不符，直接变成 B 层要重点断言的点，反过来会白跑一遍。
- 回填 `integration-cases.html`：补「实际结果」「通过/失败」两列，失败行标红并**注明归因**（前端 `Xxx.tsx:42` / 后端 `Xxx.java:88`）。
- 回填 `style-checklist.html`：逐项写结论 + **依据**；**填不出依据的写「未核对」，不要默认写「符合」**（4.6.3 反走过场约束）。不符合项要能对应到截图。
- 联调问题并入第十步的**同一张问题表**（不要另起一张），代码位置列写前端还是后端文件。

## 九、阻塞处理

遇到阻塞（接口需鉴权/登录态、服务起不来、test 库连不上、端口未知、认不出对应需求文档、**前端仓库定位不到 / dev server 起不来 / 代理没指本地后端**等）：

1. **先尽力自己找** —— 从项目配置文件、环境变量、启动脚本、本地日志 `/tmp/{项目名}-dev.log` 里找端口、连接串、token、鉴权方式；前端侧从 `vite.config.ts` / `package.json` / `pnpm-workspace.yaml` 找端口和代理配置。
2. **找不到再停下来问用户** —— 不瞎猜瞎试可能污染错误环境的操作。把缺的信息**一次性**列清楚问用户。
3. **降档要先经用户确认，不许单方面降** —— 见 4.6.1：前端没实现/没跑起来时，把「降档」当成 7.0 的不可执行项摆给用户（选项：用户给方案打通端到端 / 用户接受降档）。用户明确接受降档后，才在 HTML 和总结里写明「降档至仅契约核对，用户已确认」。
4. **环境类阻塞一律走上面的「问用户」，不许转化为跳过** —— 服务起不来、库连不上、接口要鉴权、外部依赖挂了，都属于「能解决/需要用户拍板」的问题。只允许两种收尾：**用户给方案 → 解决 → 全部用例跑完**，或**用户明确接受 → 标 `跳过-用户确认`**。
   - **禁止**在请示前就把用例划掉、禁止用「环境不通」「先不跑这些」「本次跳过」收尾，也禁止只跑一部分就汇报说测过了。

## 十、产出

- **文件产物**（落 Obsidian 需求文档目录，见 5.1）：`cases.html`（含结果回填）、`results.jsonl`、`responses/`、`run-cases.sh`；勾选了高并发/大数据量时另有 `stress-cases.html`（含执行后回填，未执行则注明「用户暂缓执行」）+ `run-stress-cases.sh` + `results-stress.jsonl` + `responses-stress/`；勾选了联调后两档时另有 `integration/integration-cases.html`（含回填与归因）+ `integration/style-checklist.html`（含回填）+ `integration/results-integration.jsonl` + `integration/screenshots/`。
- **对话内总结**（简洁，明细看 HTML）：
  - 开头注明**测试强度档位** + `cases.html` 路径；勾选了压力向用例的，注明其执行状态（已执行 / 用户暂缓）与 `stress-cases.html` 路径；**勾选了联调的，注明实际做到哪一档**（完整端到端 / 降档到仅契约核对及原因）+ `integration-cases.html` 路径。
  - 一行汇总：通过 X / 失败 Y / 跳过-用户确认 Z（压力向、联调各自单独一行汇总）。
  - **跳过清单（Z > 0 时必填）**：逐个列出跳过的用例 ID + 卡点原因 + 用户在哪一步明确接受的。**列不出用户确认记录的跳过，等于流程违规** —— 回去问用户，不要留在总结里。
  - **执行完整性一句**：脚本对账结果（`ALL_DONE expected=N actual=N`，或补齐重跑后的结果），确认本次没有任何用例是「没跑」而非「跑过/用户确认跳过」。
  - **联调各层各报一句**：A 契约核对命中几个不一致点；B1 数据断言、B2 交互断言各过了几条；C 样式核对符合 X / 不符合 Y / **未核对 W**（未核对必须报出来，不能混进「符合」），不符合项指向截图。
  - **问题清单（必须是表格，且只报告不修）** —— 本次测出的每个问题一行：

    | # | 问题描述 | 复现用例 | 代码位置 | 预期 vs 实际 | 疑似原因 | 严重度 |
    |---|---------|---------|---------|-------------|---------|-------|
    | 1 | 一句话说清坏在哪 | C03 | `Xxx.java:88` | 期望 A，实际 B | 根因判断 | 高/中/低 |

    - 严重度口径：**高**=主流程不可用/数据错乱；**中**=边界分支行为不符预期；**低**=提示语、日志、非关键字段瑕疵。
    - 「代码位置」列后端写 `Xxx.java:88`、**联调测出的前端问题写 `Xxx.tsx:42`**，一眼能看出该谁改。
    - 表格按严重度从高到低排。
    - 一个问题被多条用例命中的，合成一行，「复现用例」列写多个 ID，不要重复列。
    - **表格之后不要接「我来帮你改」并动手** —— 最多用一句话说明「要改的话大概动哪里」，然后停下等用户发话。
  - **分支覆盖情况**：未覆盖的分支及原因。
  - **本次持久化痕迹**：新增的 TestController 后门接口；造入 test 库的 mock 数据（表、主键、标记）。

## 执行顺序小结

0. `AskUserQuestion` 一次问三件（不设默认）：测试强度（轻/中/重）+ 是否覆盖高并发/大数据量 + **是否做前后端联调（不做 / 仅契约核对 / 完整端到端）**
1. 探活；服务没起 → **派子 agent 调 `start-backend`**（后台跑，只回报「起没起来+端口」），自己继续往下
2. 锁定范围（对话历史为主，git diff 为辅）
3. 找/建接口入口（缺入口写后门到 TestController，保留；新增后门需重启，同样走子 agent）
4. 读码分析分支 → 用例四要素（做什么/依赖/通过标准/入参）；勾选了高并发/大数据量的 → 追加 4.5 节压力向用例设计；**勾选了联调的 → 先按 4.6.1 查前端前置条件（不满足不自己降档，留到 6.5 问用户），再按 4.6.2 抽契约变更点、按 4.6.3 出 A/B/C 三层用例**
5. **生成 `cases.html`（及勾选时的 `stress-cases.html`、`integration/integration-cases.html` + `style-checklist.html`）落 Obsidian 需求文档目录 + `open` 打开 + 告知路径 → 不等回复，直接继续**；`stress-cases.html` 用 `AskUserQuestion` 问是否执行，**默认不执行，确认后才拉起**
6. 直连 test 库查数据，缺数据就造（加标记、不删）
6.5 **全量可执行性预检（7.0 硬卡点）** —— 逐条核验入口可达/鉴权可过/入参可造/判定依据可得/写操作不撞车/外部依赖可用，落 `cases-preflight.md`；有跑不了的，**一次性问用户**（给方案 → 解决后重跑预检全绿 / 明确接受 → 标 `跳过-用户确认`）。**还有既没预检通过、也没被用户接受跳过的用例时，不许拉起脚本**
7. 生成 `run-cases.sh`（独立并发 / 依赖串行 / **不设 curl 超时** / 结果落 `results.jsonl` / 末尾条数对账）→ **`run_in_background` 后台拉起，不同步等**；看到 `INCOMPLETE` 先补齐重跑，不拿跑了一部分的结论收尾
8. 收到完成通知 → 读结果判定 → 回填 `cases.html`
9. **联调执行**（仅勾选后两档），顺序不能反：**A 层**先做（读码 + 读 `responses/*.json` 做契约 diff，查出的问题直接变成 B 层的重点断言）→ **B1 数据断言 + B2 交互断言**（主 agent 直接用 ego-browser 交互式跑；断言写在 heredoc 里、只 print 结论 JSON、每条 append 到 `results-integration.jsonl`、截图落盘）→ **C 层**按 `git diff --name-only` 的组件清单逐个截图（含空态/长内容态）后**逐张 Read 看图**并填依据
10. 回填 `integration-cases.html` + `style-checklist.html`（失败项带归因；填不出依据的标「未核对」）
11. 阻塞先自查、不行一次性问用户（给方案 / 明确接受跳过或降档）；**任何阻塞都不允许转化为静默跳过**
12. 对话内给简洁总结（档位 + 联调档位 + HTML 路径 + 汇总 + **问题表格** + 覆盖情况 + 持久化痕迹）
13. **停手** —— 测出的问题只进表格，**后端和前端业务代码都不改**，等用户发话
