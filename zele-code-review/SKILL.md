严格对照**我的全局代码规范**审查一段改动，找出所有违反规范的地方。只审「规范符合度」这一件事，不评判需求实现对错。

## 规范来源（唯一依据）

审查**只**依据以下我的全局规范文件，不要自行发挥、不要引入文件之外的规则：

- `~/.claude/rules/coding-style.md`（代码风格与架构规范，主依据）
- `~/.claude/docs/coding-style-examples.md`（示例与反例，判定拿不准时对照）
- `~/.claude/CLAUDE.md`（个人开发规范总纲）

开审前**必须先 Read 上述文件**，把规则加载进上下文，作为子 agent 的判定标准。仓库自带的 `CODING_STANDARDS.md` 等（若有）作为补充，但**我的全局规范优先**。

## 流程

### 1. 钉住审查范围

- **默认审工作区未提交改动**：`git diff HEAD`（含已暂存 + 未暂存）。这是缺省行为，用户不指定就用它。
- 用户显式指定了固定点（commit / 分支 / tag / `HEAD~N` / `main`）→ 改用 `git diff <固定点>...HEAD`（三点，对 merge-base 比较）。

开审前确认：diff 非空（指定了固定点的话再 `git rev-parse` 确认能解析）。空 diff 或坏 ref 当场报错，不进子 agent。

### 2. 后台启动 review 子 agent（不阻塞主进程）

用 Agent 工具、`run_in_background: true` 起一个 `general-purpose` 子 agent 跑 review，**主进程不等待、不阻塞**。启动后立刻告诉用户「review 已在后台开始，你可以继续做别的，跑完我会通知你并出表格」。

子 agent 的 prompt 必须包含：
- 完整 diff 命令 + 提交列表（`git log <固定点>..HEAD --oneline`，审未提交改动时可省略）。
- **第 1 步加载的全局规范全文**（子 agent 没有别的途径拿到，必须整段贴给它）。
- 简报：「逐文件 / 逐 hunk 审查这段 diff 是否违反给定的全局规范。每条发现输出结构化字段：文件路径、行号、违反的具体规范条目（引用规范原文）、问题描述、建议改法。只报**增量代码**的问题——存量代码风格不达标不算（规范明确：增量不被存量风格影响）。工具能自动查的（编译错误等）跳过。」

> 大 diff 可按规范维度拆多个后台子 agent 并行（如「分层架构」「命名与硬编码」「注释与 JavaDoc」各一个），互不阻塞；小 diff 一个即可。

### 3. 汇总成改动表格

子 agent 跑完（后台完成会通知主进程），把发现汇总成一张表，按文件、行号顺序排列：

| # | 文件:行 | 违反规范 | 问题 | 建议改法 |
|---|---------|----------|------|----------|
| 1 | XxxService.java:42 | 魔法值 / 硬编码 | 直接写了字符串 "SUCCESS" | 提取为枚举 XxxEnum |
| 2 | XxxE.java:15 | 缺方法 JavaDoc | public 方法无注释 | 补一句话 JavaDoc |

无发现则直接报告「本次改动符合全局规范，无违规项」，流程结束。

### 4. 逐条和用户过

先展示**完整表格**让用户看全貌，然后**逐条**用 AskUserQuestion 过一遍。每条一个问题，给以下选项：

- **修复（推荐）** — 当场就改这一条
- **跳过** — 这条不改（用户认为可接受 / 存量兼容 / 属规范例外）
- **我自己改** — 用户手动处理，跳过

按用户对每条的选择执行：
- 选「修复」→ **当场直接改这条代码**，改完继续问下一条。
- 选「跳过 / 我自己改」→ 不动，继续下一条。

全部过完后，做个收尾小结：已修 N 条、跳过 N 条、用户自改 N 条，并列出已修改的文件清单。

## 边界

- 只做**规范审查 + 按用户逐条确认后修复**，不擅自大改、不重构存量代码。
- 审查依据锁定在我的全局规范文件，不夹带私货规则。
- 仅手动 `/zele-code-review` 触发。
