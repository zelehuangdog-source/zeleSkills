# test-backend-full · 后端全方位测试

写完后端、**本地已部署运行**后，手动喊我对本次改动做一次全方位测试：穷举代码分支、覆盖各中间流程字段为 null 的 case，走真实链路（调用本地服务接口）验证行为。

> **仅手动触发**（`/test-backend-full`）。不自动触发。
> **前提**：目标服务已在本地部署并运行；若没起，见「阻塞处理」。

---

## 一、确定测试范围

**范围识别优先级（重要）**：

1. **对话历史为主** —— 本次会话里刚写/刚讨论/刚改的代码，就是要测的目标。先从对话上下文锁定改了哪些类、方法、接口。
2. **git diff 为辅** —— 用 `git diff` / 最近提交做补充和交叉校验，补上对话里没显式提到但一起改动的上下游。

先把「本次改动 + 其直接上下游」列成一个待测清单，再往下走。

---

## 二、发现接口入口

测试通过**调用本地运行的服务接口**（HTTP/RPC）驱动，所以要先找到能打的入口：

1. 从改动的 Controller / 接口自动推断入口，确定 URL、方法、入参结构、鉴权要求。
2. **若改动的代码没有可直接调用的入口**（如只改了 DomainService / Repository 内部方法）：
   - 允许**写一个后门接口到对应的 TestController 类**，把要测的方法暴露出来方便驱动。
   - 位置遵循用户分层规范：`starter/controller/test/{业务模块}/XxxTestController.java`，复杂逻辑下沉到 `application/backdoor/{业务模块}/XxxBackdoorService.java`，TestController 只做接收/校验/调用/返回。
   - **这些后门代码测完保留**，作为可复用后门（符合用户 TestController/BackdoorService 后门定位）。测完在对话总结里列出新增了哪些后门接口。

---

## 三、分析分支（穷举，含深层 null）

读改动涉及的源码，**穷举所有分支**，为每条分支设计一个用例：

- 每个 `if/else`、`switch`、三元、`Optional`、循环进入/不进入。
- **每个中间流程字段为 null 的 case** —— 逐层追进被调用的方法，凡是中间过程某个字段/对象可能为 null 的分支都要覆盖。
- 输入边界：空集合、空串、超长、特殊字符、负数、零、极值。
- 状态边界：数据存在/不存在、已删除/已禁用、首次/重复。
- 依赖边界：外部服务/DB 超时、失败、返回空。

产出一个**用例矩阵**（在对话里，不落文件）：每条 = 场景 + 命中的分支 + 入参。

---

## 四、准备测试数据（直连 test 库）

- **先查后造**：直连 test 库查询是否有满足用例的现成数据，能用就用。
- **不足时直连 INSERT 造数**：test 库数据无法覆盖某用例时，直接往 test 库 INSERT 真实行来构造。
- **加可识别标记**：造的 mock 数据要能一眼区分是本次测试造的 —— 优先用带业务语义的固定标记（如名称/备注字段加统一前缀、或某个可用的标识字段写入固定测试标记）。若表没有合适字段放标记，在总结里明确列出造了哪些行（表 + 主键）供用户识别。
- **测完不删除**：造的数据保留，用户会自己看。总结里说明造了哪些数据、加了什么标记。

连接信息来源：优先从项目配置（`application-test.yml` / `application-*.properties` / 环境变量等）自己找 test 库连接串；找不到走「阻塞处理」。

---

## 五、执行测试（并发 + 判定）

**并发策略**：

- **无数据依赖的用例并发跑** —— 通过并发调接口 / 脚本并发 / 多子 agent（依当次规模自行选择）同时驱动，缩短总耗时。
- **有依赖的用例串行** —— 例如「造数 → 依赖该数据的用例」，或多个用例写同一行、有先后因果的，必须按依赖顺序串行，避免相互污染。
- 先做依赖分析把用例分组：独立组并发，依赖链内串行。

**判定（预期来源）**：

- **依代码逻辑自行推导预期并判定** —— 读源码推导每个用例的预期返回值 / 副作用（DB 变更、状态流转），调完接口后对比实际结果，自行判定通过/失败。
- 判定要具体：不只看 HTTP 200，要校验返回体字段、以及必要时直连 test 库核对副作用是否符合预期。

---

## 六、阻塞处理

遇到阻塞（接口需鉴权/登录态、服务没起、test 库连不上、端口未知等）：

1. **先尽力自己找** —— 从项目配置文件、环境变量、启动脚本、`start-backend` 相关约定里找端口、连接串、token、鉴权方式。
2. **找不到再停下来问用户** —— 不瞎猜瞎试可能污染错误环境的操作。把缺的信息一次性列清楚问用户。

---

## 七、产出（仅对话内总结）

**不落报告文件**，在对话里给出结构化总结：

- **用例结果表**：场景 | 命中分支 | 入参 | 预期 | 实际 | 通过/失败。
- **分支覆盖情况**：列出已覆盖的分支，以及未能覆盖的分支及原因（如被阻塞跳过）。
- **失败用例**：定位到具体代码位置（`file:line`）+ 现象 + 疑似原因。
- **本次产生的持久化痕迹**：
  - 新增的 TestController 后门接口（保留）。
  - 造入 test 库的 mock 数据（表、主键、标记），供用户查看。

---

## 执行顺序小结

1. 锁定范围（对话历史为主，git diff 为辅）
2. 找/建接口入口（缺入口可写后门到 TestController，保留）
3. 读码穷举分支 → 用例矩阵（含深层 null）
4. 直连 test 库查数据，不足则 INSERT 造数（加标记、不删）
5. 依赖分组：独立用例并发、依赖链串行，调接口执行
6. 依代码逻辑推导预期并判定通过/失败
7. 阻塞先自查、不行问用户
8. 对话内总结（用例表 + 覆盖情况 + 失败定位 + 持久化痕迹）
